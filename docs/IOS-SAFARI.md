# iOS Safari 版面問題與修復紀錄（2026-09-25）

在 iPhone（iOS 27 Safari）上陸續回報的跳動、白條、黑屏問題，以及最後確認的原因和修法。前面幾輪修法大多只處理了表面現象，這份文件把**真正的原因**和**已被取代的做法**分開記錄，之後遇到類似問題可以直接參考。

## 排查方法

- **iOS 模擬器**：本機已安裝 Xcode 和 iOS 27 模擬器（iPhone 18 Pro），和使用者手機的系統版本相同，大部分問題都能在上面重現。
- **即時數據面板**：網址加 `?debug=viewport` 會顯示 visualViewport、捲動位置、固定圖層位置、每次點擊與焦點變化的即時記錄。最後兩個問題的根因，都是從使用者手機上的截圖讀出來的。問題解決後已移除（`d9200f5`）。
- **重現頁**：在暫存目錄寫最小 HTML，逐幀把數值送回本機伺服器記錄，對照「Safari 原生行為」和「修正後行為」。
- **錄影逐幀**：`xcrun simctl io booted recordVideo` 錄下重新整理的過程，再用 AVFoundation 每 0.05 秒擷取一幀，找出黑屏、跳動發生在哪一幀。

## 一、點輸入框再點旁邊，整頁跳一下

**現象**：點密鑰輸入框，有時整頁（連同頂欄）往上移；點旁邊收起鍵盤時，內容再跳一下。發生與否看起來是隨機的。

**根因**：iOS Safari 在鍵盤**以原生方式打開**時，會把輸入框移到鍵盤上方空間的正中間，**即使輸入框本來就完全看得到**。移動的距離就是「輸入框中心到可見區中線」的距離：使用者手機上是 16pt，模擬器上是 6.7pt，數字完全吻合。鍵盤收起時，Safari 把頂欄和背景放回原位，頁面卻留在移動後的位置，看起來就是跳了一下。

**為什麼看似隨機**：只有鍵盤是由 Safari 原生處理打開時才會移動。從使用者的點擊記錄可以看到兩種觸發情況：

1. 剛重新整理、頁面還沒拿到系統焦點時，上一版修正「攔下點擊、改用程式聚焦」只能給焦點、叫不出鍵盤。使用者再點一次，這次交給了 Safari，於是移動。
2. 系統介面（截圖、通知等）暫時拿走鍵盤、焦點仍在輸入框上時，再點輸入框也會走 Safari 的原生路徑。

**修法**（`989b6aa`，在 `public/viewport-layout.js`）：點擊仍交給 Safari 處理，但輸入框先以 `inputmode="none"`（不開鍵盤）取得焦點，120ms 後再移除，把鍵盤叫出來。用這種方式出現的鍵盤，Safari 不會移動頁面。模擬器對照：原生點擊移動 50pt，這個做法 0pt，一般和密碼兩種輸入框都測過。這段程式放在頁面最早執行的腳本裡，所以網頁還在載入時點擊也涵蓋得到。會被鍵盤擋住的輸入框仍交給 Safari，因為它必須捲動才看得到。

**已被取代的做法**：

- 鍵盤收起後把頁面捲回原位（`84970da`、`5c87915`、`4e10cd0`）：iOS 收鍵盤時一定會自己還原一次，不管頁面怎麼補救，都會多出第二下跳動。
- 攔下點擊、改用 `focus({ preventScroll: true })`（`c0eefc1`）：剛重新整理時叫不出鍵盤，反而製造了原生路徑。
- 在密鑰欄位加上密碼管理器的忽略屬性（`0f48545`）：這項保留，因為 2FA 密鑰不是登入密碼，不該出現 1Password 的選單，但它不是跳動的原因。

## 二、輸入時錯誤提示讓下方內容上下跳

**根因**：點輸入框時會清掉密鑰下方的錯誤提示；打字時每按一鍵也先清掉，300ms 後再放回來。英文的錯誤提示有兩行（40pt），下方的設定、驗證碼和面板就跟著上下跳。

**修法**（`2cde047`）：取得焦點時不清提示；提示只在內容改變、打字停頓後直接換成新結果，中間不會先消失。

## 三、底部工具列下方的白條

**根因**：iOS 26 之後的 Safari **不會把 `position: fixed` 或 sticky 圖層畫到底部工具列那條線以下**，改用一整塊純色填滿，所以出現白條、灰條或黑條。模擬器裡試過固定圖層加高、Apple 論壇上的巢狀容器繞過方法、sticky，全部停在同一條線；只有跟著頁面捲動的內容能畫到螢幕底部。

**修法**（`be2d5ba`）：在 iOS 上，背景改為頁面的一部分，跟著頁面一起捲動。第一屏的構圖和以前一樣；往下捲時，全景接上地面延伸下去，千戀萬花的靜態圖則以倒影延伸並淡出。這也消除了背景和內容在鍵盤開關、回彈時錯開的問題。

**已被取代的做法**：

- 把背景的底色改成頁面顏色（`908e3ae`）：白條只是變成不明顯的深色，沒有解決。
- 只在頁面位於頂端時關掉回彈（`6b05ff4`，已由 `dc234f1` 撤銷）：造成無法下拉重新整理，頂部還會跳。

## 四、頁面底部的 footer 高一截、跳回去

**根因**：footer 的底部留白使用 `env(safe-area-inset-bottom)`，iOS Safari 的工具列伸縮時這個值會在 0 和約 34px 之間變化。另外，關掉回彈之後，工具列縮小時頁面會停在「超出底部」的位置，下一次觸碰時直接跳回。

**修法**：footer 在 iOS 上不使用會變動的 inset（`a6c8859` → `1c1cf13`）；iOS 保留原生回彈（`d9a4d20`），讓 Safari 平滑地拉回。

## 五、重新整理時的黑屏、綠色畫面、session 那行字跳動

用模擬器錄下重新整理的過程逐幀比對，找到四個原因（`d9200f5`、`c019df1`）：

| 現象                           | 原因                                                                                                                        | 修法                                                                                                                   |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 背景晚出現（深色模式下是黑的） | 背景圖和畫面繪製前必須執行的四支腳本，都是 `max-age=0, must-revalidate`，每次重新整理都要逐一向伺服器確認後才能使用         | 腳本網址加上內容雜湊並設為 immutable；背景、材質、音效、美術圖快取 7 天，過期後在背景更新                              |
| `/history` 黑一大段            | `/history` 設為只在瀏覽器端渲染，要等 JS 載入完才會畫出頂欄、背景和內容                                                     | 改為伺服器渲染（仍是 `no-store`、不產生共用的靜態檔）；`/2fa` 維持只在瀏覽器端渲染，網址裡的密鑰永遠不會進到伺服器渲染 |
| 綠色畫面、整頁跳動             | Safari 在內容長高後才還原捲動位置，頁面整個跳一下；跳動過程中綠色的「開始使用」按鈕經過底部工具列下方，工具列就被染成綠色   | 頁面在第一幀就是完整高度，Safari 在第一幀就還原位置，沒有跳動                                                          |
| 「This session」那行跳 4px     | 手機版的 `ore.css` 和 SessionHistory 元件各設了一個 `padding-top`，權重相同；載入過程中哪一個生效，取決於哪份樣式表最後載入 | 刪掉 `ore.css` 那一條，只留一個值                                                                                      |

**Cloudflare 的限制**：第一次部署被拒絕，因為 Nitro 會把所有帶 headers 的路由規則寫進 `_headers`，而 Cloudflare 最多只允許 100 條。原本私密頁面每種語言各佔一條，就用掉了 87 條。這些頁面其實由 Worker 回應，所以改由 Worker 的安全 middleware 設定 `no-store` 和 `noindex`，`_headers` 從 103 條降到 13 條；另外在 prerender 檢查裡加了上限檢查，超過 100 條會在建置階段就失敗。

**試過但無效**：用 `history.scrollRestoration = 'manual'` 讓重新整理回到頂端，Safari 會忽略這個設定，已撤銷（`cf1a00f`）。

## 六、Cloudflare 封鎖（未完全確認）

使用者重新整理幾次就被 Cloudflare 擋下。

- 網站程式本身**沒有任何限流**，所以封鎖來自 Cloudflare 控制台的設定，例如 Rate limiting 規則、WAF 自訂規則、Bot Fight Mode 或 Security Level。
- 修正前，每次重新整理除了 HTML，還會對每支腳本和每張背景圖（全景有 6 張）各發一次重新驗證請求，一次重新整理就是十幾個請求，很容易觸發以「每 10 秒 N 個請求」計算的規則。`d9200f5` 之後，重新整理時這些都直接使用瀏覽器快取，請求數大幅下降。
- **仍需在控制台確認**：到 Security → Events，用自己的 IP 或 Ray ID 篩選，就能看到是哪一條規則擋下的。如果是 Rate limiting 規則，建議只計算 HTML 頁面的請求（排除 `/_nuxt/`、`/panorama/` 和其他靜態副檔名），或提高門檻。

## 教訓

- 先量測再修改。前幾輪都是依照症狀猜測原因；直到有了即時數據面板和模擬器，才看出是 Safari 置中輸入框和固定圖層這兩個機制。
- 「補救」式的修法（事後捲回、修改顏色）都會留下第二個跳動或另一種白條；要從不觸發原生行為、或不依賴固定圖層的方向解決。
- Safari 的行為要用和使用者相同的 iOS 版本驗證。這次使用者和模擬器都是 iOS 27，模擬器重現的結果和手機一致。
